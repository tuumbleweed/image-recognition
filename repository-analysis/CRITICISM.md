# Review Findings

## Remaining Issues

- **Forward and backward mathematics disagree (confirmed).** `src/network/cpu.cpp` and `src/network/gpu.cu` apply sigmoid in every forward layer but use ReLU derivatives for hidden-layer backpropagation. Output derivatives call sigmoid again on an already activated output. These updates are not the derivatives of the implemented forward computation. Use matching activation/derivative pairs, preserve pre-activations where necessary, and verify small networks with finite differences before comparing accuracy.
- **Batch updates use a shared delta (confirmed).** `train_on_a_batch_cpu/gpu` average activations and one-hot labels before calculating deltas; both backpropagation functions then reuse those deltas for every example’s previous activations. This differs from averaging per-example gradients and can obscure example-specific errors. Compute each example’s delta from its own activations and label, then average parameter gradients. CPU/GPU agreement alone cannot validate this shared algorithm.
- **Input and option validation is incomplete (confirmed).** IDX readers in `src/io/io_utils.cpp` do not validate magic numbers, dimensions, successful reads, or image/label count agreement. Failed opens return empty data and execution continues. A zero batch size reaches modulo-by-zero in `src/network/train.cpp`; zero testing examples produce an undefined accuracy ratio. Validate data and options before initialization/training and define a training-only result when testing is disabled.
- **Diagnostics do not establish numerical correctness (confirmed).** `MatrixMult` prints outputs without assertions. Its CUDA helper launches a two-dimensional block while the kernel indexes only the x dimension, causing duplicate writes; its grid is sized from input width instead of output count. `CudaInspection` reads an uninitialized character buffer through `device_strlen`. Correct these harnesses and add targeted gradient and CPU/GPU comparison checks with tolerances.
- **Portability and numerical parity need qualification (confirmed).** CMake requires CUDA even for CPU runs and hard-codes architecture 89 and `-mfma`. GPU sigmoid uses single-precision `expf` despite double storage, whereas CPU uses `std::exp` on doubles. Make target architecture/toolchain options configurable, allow CPU-only builds, and use deliberate precision consistently. Do not claim exact CPU/GPU equality from the existing logs.

## Simplification Opportunities

- **Reuse GPU scratch memory and reduce transfers.** Network weights persist across training, but `forward_propagation_gpu` allocates input memory per image and copies each layer’s activations to the host. Backpropagation allocates scratch buffers per batch, transfers previous activations back, and unconditionally copies diagnostic gradients to the host although their printing is commented out. A reusable workspace and optional diagnostic transfers would reduce overhead without changing the learning objective.
- **Reduce redundant CPU copies and GPU atomics.** CPU accumulator networks are passed by value through several layers of calls. GPU accumulation currently runs sequentially on the default stream with one thread owning each output row, so atomic updates appear unnecessary for this launch scheme. Reuse an explicitly cleared accumulator by reference and use ordinary additions unless batch parallelism introduces shared writers.
